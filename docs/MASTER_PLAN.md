# 3mm — общ продуктов план и разпределение по чатове

Обновен: 2026-10-08. Статус: план; внедреното и приетото са изрично отбелязани.
Този документ задава общата последователност; техническият Roadmap и отделните
планове пазят подробностите и доказателствата за приемане. Не отваряме наново
завършени задачи и не преименуваме историческите milestones.

Следващ одобрен Core milestone: **20 — Extension Platform v2**, със старт WP0
(налично → липсващо). Одобрен е планът; реализацията още не е започнала.

## Цел

Един универсален 3mm Core върху Raspberry Pi или поддържан Linux сървър.
Клиентът може да работи само локално или локално и с облака едновременно.
Нашата централна инсталация също е 3mm, с отделно инсталирани extensions за
сайт/магазин, управление на инсталации и платени функции. Няма отделен cloud Core.

Под „сайт, който хоства app-а“ засега разбираме публичен сайт и клиентски портал
върху наша централна 3mm инсталация. Linux машината хоства процесите; extension-ът
добавя страниците и бизнес функциите. Хостване на пълни клиентски приложения с
техните бази данни е отделна бъдеща услуга, не подразбиращо се следствие от портала.

## Граници на компонентите

| Компонент | Отговорност | Не поема |
| --- | --- | --- |
| Core / SDK / Agent / Setup | Общи права, идентичности, договори, устройства, инсталиране, update/restore | Магазин, конкретен платежен доставчик или клиентско приложение |
| Локален Fleet extension | Настройване и управление на Nodes през техния Hub | Собственост върху всички клиентски инсталации |
| Cloud Management extension | Организации, собственици, покани, инсталации, видимост и одобрена поддръжка | Втори пряк команден авторитет за Node |
| Website / Store extension | Публични страници, каталог, клиентски профил, поръчки, checkout и плащания | Root управление на сървъра или права за физически устройства |
| Entitlements extension | Планове, покупки/абонаменти и подписани разрешения за платени функции | Онлайн разрешаване на всяка локална операция |
| Theme extension | Версиониран визуален пакет върху общия Core Theme API | Маршрути, права, бизнес логика или изпълним код |
| Showcontroller extension — бъдеща миграция | Функциите на съществуващия самостоятелен app като отделно инсталиран пакет | Второ ядро, собствени паралелни потребители или задължителен облак |
| Embedded Nodes extension / firmware — бъдещ етап | Board profiles, provisioning helpers, firmware и embedded diagnostics | Втори device registry или ESP-specific логика в Core |
| Клиентски extensions | Конкретни приложения върху общите capabilities | Промяна на Core за конкретно име на extension |

Имената на бъдещите extensions/repos са работни, не вече създадени продукти.
Ако друг чат вече има подходящ пакет, преглеждаме и надграждаме него.
Локалният Fleet остава отделен от централния мениджър. Бизнес extensions имат
собствени пакети/версии и използват общи договори, а не директен достъп до чужди БД.

## Какво е потвърдено и какво не е

- Има Hub/Node сдвояване и успешна физическа LED проба на Zero W ARMv6.
- На 2026-10-01 потребителят потвърди успешен реален Hub -> Node update.
  Основният OTA сценарий е приет по негово съобщение; има още неописани бъгове.
  Това не затваря rollback/reboot/network acceptance или целия локален комплект.
  Версиите и финалният operation report още не са приложени към тази проба.
  Стабилизацията остава в OTA чата, без паралелни корекции от този чат.
- Release builder-ът публикува full пакети за `aarch64`, `armv7l`, `x86_64`.
- На 2026-10-04 собственикът потвърди, че CME и Fleet са в работещо положение.
  Това е продуктова отправна точка, не автоматично приемане на всички негативни,
  recovery и production security сценарии.
- На 2026-10-08 собственикът прие Theme Platform / Milestone 17 за приключен
  след публикуването на beta.43. CI/release са успешни; разширените live
  rollback/restore проби остават общи platform-stability проверки, не преминали тестове.
- Installer/preflight вече поддържа `x86_64` и wired-only host без задължителен
  `wlan0`/Setup AP. VM update и Core/Agent readiness са проверени от потребителя;
  пълният clean Linux server acceptance остава отделна неприключена проба.
- Текущите installer профили са само `full` и `node`. Сървърен режим е планиран;
  не даваме на потребители несъществуващ installer флаг.
- Публичният магазин и лицензите не се приемат за готови без проверка на
  съответните пакети и реален сценарий.
- Core G1–G4 договорите за идентичност, одобрени peers и ограничен статус са
  реализирани и минали изолирана Raspberry HTTPS/socket проба; включени са в
  release обхвата на beta.31. Тази конкретна проба не е проверявала реалната CME
  организация/Owner UI или публичния HTTPS ingress; текущият работещ CME статус
  е последващото потвърждение на собственика, описано по-горе.

## Последователност

### A. Завършен локален комплект; Linux server baseline е отложен

Запазваме досегашния ред: приключване на OTA; първа настройка без SSH;
backup на Hub -> нова карта -> restore -> повторно свързване на същия Node,
включително идентичности, сдвояване и доверени update ключове.

Linux server baseline е **отложен по решение на собственика от 2026-10-01**.
Връщаме се към него, когато потрябва сървър за реално хостване. Не е текуща задача
и не блокира планирането на общите договори и extensions.

Запазен бъдещ обхват за Core/deployment: първи Linux server target — Debian
`x86_64` със systemd; точната версия се фиксира преди теста. Същите releases,
една bootstrap команда, immutable activation, health checks и rollback.
Server настройването е през съществуващата LAN връзка, без задължителни Wi-Fi,
AP или GPIO. Не инсталираме/сменяме мрежовия мениджър и не прекъсваме SSH като
страничен ефект. Няма нова cloud device role: централните функции са extensions.

Приемане: clean VM/машина -> setup и сигурен администратор -> app -> restart ->
update/rollback -> backup/restore; адресът и съществуващата мрежа се запазват.
Други дистрибуции, Docker, HA и нова БД не са обещани с тази първа доставка.

### B. Общи Core/SDK договори за инсталации и услуги

Първо проверяваме вече наличното. Добавяме само доказано липсващите договори:
отделна идентичност на инсталацията; изходящо enrollment с изрично одобрение;
отделни от Node pairing credentials; ограничени оттегляеми права;
версионирани събития между extensions и общ договор за проверка на подписан grant.

Организации, планове, продукти и поръчки остават в extensions. Всеки чат дава
точно Core/SDK задание при липса, вместо сам да добавя специален endpoint или
заобикаляне на достъпа. Application/installation access не е Node command authority.

### C. Cloud Management — първо само видимост

Клиентският Hub се свързва навън към избран централен адрес, например
`https://3mm.config.bg`; няма твърдо зададен домейн или задължителен cloud акаунт.
Показваме само одобрени инсталации, Nodes, версии, online/offline и избрани
диагностични данни. Клиентски бизнес данни не се копират по подразбиране.

Приемане: две организации и два Hubs; нито UI, нито API разкрива чужда инсталация;
enrollment може да се отмени; загуба на интернет не спира локалния app.
Собствеността се доказва, не се присвоява по hostname, email или свободно device ID.
Свързване/споделяне между клиентски инсталации изисква отделно делегиране от
съответните собственици; общ собственик не означава автоматичен достъп.

TLS, отделни credentials и проверка на клиентската изолация предхождат публичното
излагане. Cloudflare е инфраструктурен вариант, не заместител на тези проверки.
Обновяване и временна поддръжка идват след read-only приемането, с одобрение,
одит и rollback. Node продължава да получава команди само през локалния Hub.

### Следващ Core milestone — Extension Platform v2

Одобрен на 2026-10-07 като [Milestone 20](ROADMAP.md#milestone-20--extension-platform-v2).
Подробният [Core план](../EXTENSION_PLATFORM_V2_CORE_PLAN.md) развива наличната
платформа, без втори extension/device subsystem. Обхватът е общ за Standalone,
Hub/Fleet, local Agent и application extensions; Fleet/облакът не са условие.

Първо **WP0**: карта „използваме → допълваме → липсва → отлагаме“, с проверими
доказателства, текущи версии, съвместимост, security граници и един малък първи
резултат. Това е анализ/договор, не нов runtime. SDK 1.3, идентичностите,
данните, конфигурацията, правата и device bindings се запазват. Номерът „v2“ на
плана не преномерира автоматично manifest, SDK или Core release.

След приемането на WP0: общ модел и публични договори с ранен isolation design;
локален package и доказана изолация/approval/rollback; пълен lifecycle/recovery;
registry distribution; накрая optional offline entitlements. Signature,
publisher trust, runtime policy и разрешени права са отделни проверки.
Capability invocation остава през общия provider-neutral Device слой, без
паралелен GPIO/Fleet механизъм. Rollback не повтаря неясни външни плащания или
физически действия; управлението и recovery не зависят от cloud/лиценз.

Marketplace и AI Generator са отделни consumers на приетите договори, не
нова реализация вътре в Core. WP0 съпоставя overlap с M15/M16; M17 е приключен
по финалното приемане на собственика, а отложеният ESP M18 не блокира M20.
В тази редакция не започваме код, release или live промени.

### Приключена UI линия — Core Theme Platform и теми като extensions

Одобрено на 2026-10-04. [Milestone 17](ROADMAP.md) и
[Theme Extension Plan](THEME_EXTENSION_PLAN.md) следват посоката от чата
„Предложения за тема“: професионален product интерфейс и отделно marketing UI.
В Core остават общият Theme API, валидаторът, registry, изборът на тема и
безопасното прилагане на tokens. Конкретните палитри/дизайни са отделни ZIP
extensions; marketing страниците са отделно приложение, не Theme permissions.

T0–T3 са публикувани в `v0.3.0-beta.36`: строг `theme-extension v1`, общият
Extensions upload/catalog/lifecycle, избор в Settings и loader с fallback.
Локалният Graphite Mint v1 е палитра, не цялостен нов layout; live/portable
theme acceptance остава отделна проверка.

На 2026-10-05 обхватът е разширен с [Theme Platform v2](THEME_PLATFORM_V2_PLAN.md):
shared UI primitives, Core-owned sidebar/top-navigation shell, типография,
плътност, component variants и safe local assets. V0–V4 са публикувани;
работещата основа и персоналните цветове на темите са в `v0.3.0-beta.40`.
На 2026-10-07 V5 е реализиран и проверен локално: installed-package preview/
Cancel/Apply, два действителни reference ZIP пакета и лицензиран шрифт с кирилица.
Общият Extensions installer, reload и desktop/mobile light/dark/BG/EN са проверени
в изолирана среда; виж [отчета V5](THEME_PLATFORM_V2_V5_REPORT.md).
V5 е одобрен от собственика; общият редактор и запазването на темата при временен
мрежов отказ са доставени в `v0.3.0-beta.41`. V6 / DashboardList, Extensions,
Settings и Display Editor и V7 / публичен UI договор са одобрени и публикувани
в `v0.3.0-beta.43` с успешни CI/release проверки. На 2026-10-08 собственикът
приема резултата за приключен: **M17 е затворен**.
Разширените live rollback/restore проби не са потвърдени с отделен отчет;
проследяват се като общи platform-stability проверки, без нова theme реализация.
Конкретните theme ZIP пакети не влизат в Core release. Запазваме v1
пакетите, старите настройки и единния upload през Extensions. Settings,
Header/Menu Customization, i18n, права и dynamic registrations се запазват;
конкретната theme не заменя router, auth, handlers или Core Vue компоненти.
Device protocol, Agent и Application SDK не се преработват за визуални теми.

Приемане: upload -> избор -> light/dark -> reload -> disable/uninstall ->
вградена тема; без загуба на старите настройки и без rebuild на Core за нова
тема. Работи локално и без облак, еднакво за Standalone и Hub/CME интерфейс.

### D. Публичен сайт, клиентски портал и магазин

Първа доставка: многоезични публични страници и каталог; клиентски профил,
поръчки и checkout с един избран доставчик в тестова среда. Публичните маршрути
са изрично декларирани и не отварят административния API.

Статусът „платено“ идва от проверено сървърно известие/потвърждение, не от
успешно връщане на браузъра. Не съхраняваме картови данни. Ключовете са secret
references. Дублирани известия, загубен отговор, рестарт и refund/cancel имат
ясни състояния и не създават повторна поръчка или разрешение.
Ако SDK не поддържа нужните подписани callbacks, първо описваме generic ingress
договор; не добавяме платежния доставчик по име в Core.

Приемане: sandbox покупка -> проверено плащане -> устойчиво събитие за покупката;
повторно известие няма втори ефект. Реални плащания се включват отделно след
одобрени условия и готов договор с Entitlements, не при първия checkout тест.

### E. Платени функции и офлайн разрешения

Entitlements обработва проверената покупка през общ договор и издава подписан
grant за определена инсталация, функция и срок. Core проверява локално подписа
и ограниченията, без да знае имена на продукти или да пита магазина при всяко действие.
Покупка/лиценз не заменя локалните потребителски права и изричното одобрение.

Преди реализация уточняваме единицата за продажба, trial, офлайн валидност,
изтичане, часовник, подновяване, refund и ограниченията на отмяна без интернет.
Няма общо дистанционно изключване на app-а или аварийни физически действия
при проблем с плащане. Безплатните локални функции не изискват cloud enrollment.

Приемане: покупка -> едно разрешение -> разрешена функция локално; изключен
интернет запазва договорената офлайн работа; чужд, подправен или неподходящ grant
се отказва. Цени, доставчик и търговски условия още не са избрани.

### F. Следващи реални capabilities

Когато е наличен четец: идентификатор -> решение от extension -> безопасен GPIO
импулс, с измерване на латентност и поведение без интернет. Това е универсален
договор, не Child Center логика в Core. Няма обещание за поддръжка преди хардуерна
проба. Работата може да върви независимо от сайта след локалното приемане.

### G. Showcontroller — от самостоятелен app към extension

Бъдеща отделна продуктова линия: мигрираме съществуващия Showcontroller към
инсталируем 3mm extension със собствен пакет, версия и lifecycle. Това не е
задача за реализация сега и не блокира Linux server или локалния Fleet.

Първо преглеждаме текущия app: функции, данни, конфигурации, ресурси и хардуерни
интеграции. Избираме един представителен работещ сценарий за първия пакет, вместо
пълно пренаписване наведнъж. Нужните media/timing/device договори се определят
от тази проверка; общите възможности се дават от Core/Agent, а конкретните
сценарии и интерфейс остават в extension-а. Управлението на хардуер минава през
декларирани capabilities, не чрез директен привилегирован достъп от extension-а.

Използваме 3mm потребители, права, динамични маршрути, update и recovery.
Планираме проверим import на старите проекти/настройки и ресурси, без загуба
на оригинала; самостоятелният app остава достъпен до приемане на миграцията.
Приемане: същият избран сценарий работи локално, включително без интернет;
измерени timing ограничения; disable спира изпълнението, без да трие проектите;
backup/restore и неуспешен update запазват данните и не повтарят физически действия.
Точният функционален обхват остава отворен до преглед на Showcontroller.

### H. Platform-neutral Nodes — реализирана обща Core основа

[Планът C0–C14](PLATFORM_NEUTRAL_NODES_PLAN.md) вече има локална реализация и
regression проверки; C14 consumer UI/live acceptance остава отделна проверка.
Запазваме peer v2 / SDK 1.3. Това е общият Device Platform за Standalone,
local Agent, Hub/Fleet и application extensions, не Fleet-only слой.
Mock embedded остава архитектурното доказателство и regression reference.
Не отваряме нов Core refactor само за конкретен ESP чип.

### I. 3mm Embedded v0.1 — към края, когато има хардуер

[Milestone 18](ROADMAP.md) / [Embedded Nodes Extension Plan](EMBEDDED_NODES_EXTENSION_PLAN.md)
е запазен бъдещ етап. В чата „Разширяване към ESP чипове“ е потвърдено, че
нямаме наличен ESP; не започваме firmware или board-specific код сега.
Първо един reference board, устойчиви identity/credentials, Wi-Fi provisioning,
enrollment, heartbeat и една физическа capability през общите Core договори.
После отделен Embedded Nodes extension за настройване, диагностика и OTA UI.

Core е стабилен dependency: board profiles, драйвери, pin mapping, firmware
каталог, provisioning и OTA implementation остават извън него. Нов Core договор
се предлага само при доказана обща липса, не при всяка embedded задача.
Този етап не блокира темите, сайта, CME, Fleet или локалната работа.

## Разпределение по чатове

Този чат пази общия план, зависимостите и приемането. Следните са направления
за съществуващи или изрично поискани нови чатове, не вече изпратени задачи:

1. **Core / SDK / Linux** — общите договори от B и следващият Milestone 20,
   започващ с WP0; server baseline само при възникнала нужда и отделна заявка;
   без бизнес UI и без реализация на AI Generator/Marketplace.
2. **Локален Fleet / Zero** — текущо OTA, настройване без SSH и физическо приемане.
3. **Cloud Management extension** — собственост и read-only видимост, после поддръжка.
4. **Website / Store extension** — публичният сайт, клиентският портал и sandbox checkout.
5. **Entitlements extension** — търговски модел и подписани офлайн разрешения.
6. **Клиентски приложения** — самостоятелни extensions; подават конкретни SDK липси.
7. **Showcontroller migration** — отделен бъдещ чат за оценката и поетапното
   прехвърляне на самостоятелния app към extension; Core/SDK липсите се предават на 1.
8. **Теми / визуален дизайн** — конкретни themes върху общия Theme API;
   общият Core UI слой и v2 договор са доставени с приключения M17. Дизайнерският
   чат може да изготвя отделните пакети по приетия договор; общите Core файлове
   не се редактират паралелно. Marketing страниците остават при направление 4.
9. **Embedded Nodes / ESP** — бъдещи firmware и extension извън Core;
   започва при наличен хардуер след generic contract acceptance.

За всяка малка задача: текущ repo/branch/commit и чужди промени; използвани версии
на договорите; точен обхват и файлове; един демонстрируем резултат; кратки целеви
проверки; ограничения и статус. Auth, migration, плащания и физически операции
изискват съответните проверки, дори при ограничен бюджет. Не пускаме тежък deploy
или целия test suite за редакция на план. Общите Core файлове имат един изпълняващ
чат наведнъж; нуждите на останалите се предават като конкретно задание.

Създаване/изпращане на задачи, commit, push, release и live промени стават само
по изрична заявка. Linux server baseline е отложен до реална нужда;
останалите локални OTA проби продължават отделно. Следващият одобрен Core
milestone за този чат е Extension Platform v2, започващ с WP0 след изрична
заявка за работа. Theme Platform / M17 е приключен по приемане на собственика;
конкретни теми и миграция на чужди extension интерфейси остават отделни задачи.
